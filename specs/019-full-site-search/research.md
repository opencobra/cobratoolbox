# Research: Full-Site Documentation Search

## Context established during investigation

Before any design decision, the current pipeline and search implementation were traced end
to end (repo: `cobratoolbox-f-develop`, plus the published output checked out at
`cobratoolbox-gh-pages`).

### The publish pipeline

`.github/workflows/build-and-publish-docs.yml` runs on every push to `master`. It: installs
`documentation/requirements.txt`, runs `make html` (Sphinx, `documentation/Makefile`) twice
(once before and once after generating function/citation RST via
`documentation/source/modules/GetRSTfiles.py` and
`documentation/source/sphinxext/GenerateCitationsRST.py`), stages the freshly built
`documentation/build/html/` into `ghpages/stable/`, separately checks out the *existing*
`gh-pages` branch read-only and copies its `stable/tutorials/` folder into the new staging
area verbatim (tutorials are **not** rebuilt from `.rst` each run — they persist across
deploys as pre-built HTML), then deploys the merged `ghpages/` tree to `gh-pages` via
`JamesIves/github-pages-deploy-action@v4`.

### The current search bar (the thing being replaced)

The sidebar search box present on every page (`<input id="simple">`, visible in the built
`index.html`, `faq.html`, `installation.html`, every `modules/**/index.html`, etc.) is a
jQuery `easyAutocomplete` widget. Its config (embedded inline in each page, via the theme's
layout template) points at `_static/json/functions.json` — a flat list of
`{"name": <MATLAB function name>, "website_url": <link>}` records, nothing else. This is
the literal cause of the reported problem: the box only ever has function names to match
against.

Separately, Sphinx's own generic full-text search already exists on this site
(`search.html` + `searchindex.js` + `_static/searchtools.js`, generated automatically
by `make html`) and **already indexes the full text of every `.rst`-generated page**,
function reference pages included. It is reachable today only by submitting the sidebar
form (pressing Enter), which navigates to `search.html` — visitors do not see this
capability through the instant-lookup box they actually use.

### Where `functions.json` actually comes from — and why that matters

No script committed in this repository and no step in `build-and-publish-docs.yml` writes
`_static/json/functions.json`. `documentation/generateJSONList.py` produces a file with that
exact name/shape but is **not invoked anywhere in the CI workflow** (confirmed by reading
the workflow file top to bottom — grep for `generateJSONList` and `createModulesPage.sh`
both return only the local, uncalled scripts themselves). The site's HTML theme,
`html_theme = "sphinx_cobra_theme"` (`documentation/source/conf.py`), is installed at build
time straight from `git+https://github.com/opencobra/sphinx_cobra_theme.git@develop`
(`documentation/requirements.txt`) — it is not vendored anywhere in this repository, not
even under `external/`. The search-box markup and its `functions.json` wiring are therefore
almost certainly generated by that external theme package itself (most likely a bundled
static/template file, or a Sphinx build-event hook it registers), not by anything this repo
controls directly.

This is the load-bearing fact for the whole plan: per Constitution Principle V/IX, this
feature cannot edit `sphinx_cobra_theme` — it is not part of this repository's tree at all,
so there is nothing here to "avoid editing," but there is also nothing here we can patch
directly. The only paths this repo can act through are (a) Sphinx's standard local template
override mechanism, and (b) new/extended Python steps in the existing publish pipeline.

### The local template-override mechanism already exists in this repo

`documentation/source/conf.py` sets `templates_path = ['_templates']`, and
`documentation/source/_templates/` already contains repo-local overrides of theme templates
(`index.html` extends the theme's `layout.html` and overrides just the `body` block;
`indexsidebar.html` is a similar partial override). This confirms the established,
already-used mechanism for changing what an external theme renders without touching the
theme's own repository: drop a same-named template into `documentation/source/_templates/`
and Sphinx's template loader prefers it over the theme's copy. The search box template
(commonly named `searchbox.html` in Sphinx-RTD-derived themes) is the template this feature
needs to override the same way, once its exact name is confirmed against the installed
theme package during implementation (Sphinx logs the resolved template search path with
`-vv`; this is an implementation-time confirmation step, not a planning blocker).

## Decisions

### Decision 1 — Reuse Sphinx's existing full-text index rather than building a new one

**Decision**: Feed the instant-lookup search box from Sphinx's own generated
`searchindex.js` (via its existing `_static/searchtools.js` search/scoring code)
for all content that Sphinx rebuilds from `.rst` each run — function reference pages,
installation, FAQ, guides, contributing, citations. Do not hand-roll a second indexing/
matching pipeline for that content.

**Rationale**: Sphinx already builds this index on every `make html` run at zero extra
maintenance cost, it already covers function reference pages (satisfying the "no regression
to function search" requirement, FR-003/SC-002, for free — Sphinx's index actually goes
deeper than the current name-only list, matching within docstring text too), and its
scoring/matching code is a proven, already-shipped part of the toolchain rather than new
attack surface. The only real gap is that today's UI never shows this index to the visitor
except via the separate `search.html` page.

**Alternatives considered**:
- *Extend `generateJSONList.py` into a full custom content index* (title + body text for
  every page, all page types) and add a bespoke client-side matcher. Rejected: duplicates
  work Sphinx already does correctly for the `.rst`-generated majority of the site, adds a
  new indexing format to maintain, and still would not explain/fix the fact that
  `functions.json` generation is currently not wired into CI at all.
- *Point the CI at generating `functions.json` via `generateJSONList.py`, keep the
  name-only widget, just also make the separate `search.html` more discoverable.* Rejected:
  does not satisfy FR-001 (matches must come from the box itself, not a second page the
  visitor has to navigate to) or the user's explicit request to change the search bar
  itself.

### Decision 2 — Supplement the index with a small, purpose-built tutorial index

**Decision**: Because tutorials are carried over as pre-built HTML rather than regenerated
from `.rst`, they are absent from Sphinx's `searchindex.js` by construction. Add one new,
narrowly-scoped Python step to the existing publish pipeline (same family as the existing
`UpdateSideBar.py`/`GenerateCitationsRST.py` steps) that walks the tutorial HTML staged for
publish (`ghpages/stable/tutorials/`, after the existing "Bring existing tutorials into
staging" step) and emits a small supplemental JSON index (title, extracted text, URL) in the
same shape the search widget already consumes. The widget queries both sources and merges/
ranks results before rendering.

**Rationale**: Keeps the tutorials gap closed (FR-008, the clarified requirement) without
forcing tutorials into Sphinx's own build (a much larger change: tutorials are not `.rst`
sources at all, and their independent lifecycle — added/removed outside this repo's publish
run — is out of scope here). A small, single-purpose script mirrors the pipeline's existing
pattern for post-processing already-staged HTML (`UpdateSideBar.py` already parses staged
HTML with `html5lib` for a different purpose in the same job).

**Alternatives considered**:
- *Skip tutorials for v1.* Rejected per the explicit clarification resolved during
  `/speckit-specify` (tutorials are in scope).
- *Rebuild tutorials from source every run so they become ordinary Sphinx pages.* Rejected
  as out of scope — tutorials' build/carry-over mechanism is a pre-existing, independent
  part of the pipeline this feature has no stated mandate to restructure, and doing so would
  vastly widen the change's blast radius for a search-indexing feature.

### Decision 3 — Override the theme's search box template locally; do not touch the theme repo

**Decision**: Add `documentation/source/_templates/searchbox.html` (exact template name to
be confirmed against the installed `sphinx_cobra_theme` package at implementation time,
following the pattern already used by `_templates/index.html`) that replaces the current
`functions.json`-only `easyAutocomplete` wiring with logic that queries the merged index
from Decisions 1–2 and renders ranked, linkable results with enough context to judge
relevance (FR-002).

**Rationale**: `sphinx_cobra_theme` lives in a separate GitHub repository
(`opencobra/sphinx_cobra_theme`) fetched via pip at CI build time — it is not part of this
repository's tree (not even under `external/`), so Constitution Principle V's "read-only,
vendored, third-party paths MUST NOT be edited" has no path to point at here; there is
simply nothing to edit. Sphinx's template-override mechanism is the sanctioned way to change
themed output from within `documentation/source/`, and this repo already relies on it for
two other templates.

**Alternatives considered**:
- *Fork/patch `sphinx_cobra_theme` directly.* Rejected: out of this repository's boundary
  entirely; would require a separate feature/PR against a different repository and is not
  something this Spec Kit feature can approve or scope.
- *Post-process the built HTML with a script (à la `UpdateSideBar.py`) to inject different
  markup/scripts after the fact.* Considered viable as a fallback if the template-override
  name cannot be confirmed at implementation time, but the template override is preferred as
  the more direct, already-precedented mechanism.

### Decision 4 — Keep the instant, type-ahead interaction; do not introduce a results page

**Decision**: The rewired widget continues to render results inline beneath the search
input as the visitor types (same interaction shape as today's `easyAutocomplete` box), now
backed by the broader merged index instead of `functions.json` alone.

**Rationale**: FR-005 and the site's existing, validated UX pattern (Assumptions in
`spec.md`) both call for keeping this interaction; Sphinx's search-index format is designed
to be queried client-side without a page load, so nothing about broadening scope forces a
navigation-based results page.

**Alternatives considered**: Send the query straight to the existing `search.html`. Rejected
per FR-005 — that page requires a full navigation before the visitor sees whether anything
matched, which the user's request (and the current widget's UX) explicitly moves away from.

## Open items — resolved during implementation (T001/T002)

- **Template name — resolved**: `sphinx_cobra_theme==0.0.1` (installed fresh from
  `git+https://github.com/opencobra/sphinx_cobra_theme.git@develop`) ships
  `sphinx_cobra_theme/searchbox.html` (found via
  `python -c "import sphinx_cobra_theme; print(sphinx_cobra_theme.get_theme_dir())"`). Its
  `layout.html` includes it verbatim: `{% include "searchbox.html" %}` inside the
  `sidebartitle` block. It is exactly the `<div role="search">`/`easyAutocomplete`/
  `functions.json` block already identified from the live site. Overriding
  `documentation/source/_templates/searchbox.html` in this repo is confirmed sufficient —
  Sphinx's template loader resolves `_templates/` before the theme's own copy for any
  same-named template, exactly like the existing `index.html` override.
- **`searchindex.js` location and format — resolved (and corrected from this document's
  earlier draft)**: a full local build (`sphinx-build -b html source build/html`, Sphinx
  6.2.1) confirmed the file lands at the *build root*, `build/html/searchindex.js` — **not**
  under `_static/`, contrary to this document's earlier phrasing (now corrected throughout).
  Its content is a single statement, `Search.setIndex({...})`, with keys `docnames`,
  `filenames`, `titles`, `terms`, `titleterms`, `objects`, `objnames`, `objtypes`,
  `alltitles`, `indexentries` — confirmed by reading both the generated file and
  `_static/searchtools.js`'s own references to `Search._index.*`. Because it is a executable
  script statement, not JSON, the correct client-side loading mechanism is the same one
  Sphinx's own `search.html` uses: `Search.loadIndex(url)` appends
  `<script src="searchindex.js">` to the page, which runs and calls the global
  `Search.setIndex(index)`. `siteSearch.js` (T004) reuses this exact mechanism rather than
  fetching and JSON-parsing the file.
- **Scoring reuse — refined**: `_static/searchtools.js`'s `Scorer` object (title/term/
  partial-match weights) is a plain, DOM-independent config object, safely reusable as-is.
  `Search.performSearch`/`Search.query`, however, are tightly coupled to rendering into
  `search.html`'s specific DOM (`#search-results`, paginated via `setTimeout`) — not suited
  to an inline type-ahead dropdown. Refined approach: load the real `_static/searchtools.js`
  on every page (so its `Search`/`Scorer` globals exist), let `searchindex.js` populate
  `Search._index` via the real `Search.setIndex`, then have `siteSearch.js` read
  `Search._index` directly and run its own small ranking loop (reusing `Scorer`'s weights for
  consistency with Sphinx's own ranking) rather than calling `Search.query`. This still
  satisfies Decision 1's intent — no second indexing pipeline, and ranking behavior matches
  Sphinx's own weighting — while producing output shaped for an inline widget instead of a
  full results page.
- **Payload size — measured**: a full local build including all function reference pages
  (284 `modules/**/index.html` pages) produced a 1.1 MB `searchindex.js` (versus 288 KB for
  narrative-only content before function RST generation). At typical gzip compression for
  this kind of repetitive JSON-like text (commonly 70-80% for this content shape), this is
  consistent with SC-003's <1s target on standard broadband; no chunking/lazy-loading is
  needed for v1.
