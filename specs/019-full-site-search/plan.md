# Implementation Plan: Full-Site Documentation Search

**Branch**: `019-full-site-search` | **Date**: 2026-08-17 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/019-full-site-search/spec.md`

## Summary

Replace the website's sidebar search box — currently an `easyAutocomplete` widget backed
only by a function-name list (`_static/json/functions.json`) — with a full-site, instant
type-ahead search that also matches installation, FAQ, guides, contributing, citation, and
(per the resolved clarification) tutorial content. Technical approach: reuse Sphinx's own
already-generated full-text index (`searchindex.js`) for everything the build
regenerates from `.rst` each publish, add one small new pipeline step that emits a
supplemental JSON index for tutorial pages (which are carried over as pre-built HTML rather
than rebuilt from source each run), and override the theme's search-box template locally
under `documentation/source/_templates/` — the theme itself
(`opencobra/sphinx_cobra_theme`) is a separate, out-of-repo GitHub project and is not
edited. See `research.md` for the four architectural decisions and why each was chosen.

## Technical Context

**Language/Version**: Python 3.10 (matches `documentation/requirements.txt` /
`setup-python` in CI) for the new indexing step; JavaScript (browser, no build step —
matches the existing theme/`easyAutocomplete`/Sphinx `searchtools.js` style already on the
site) for the rewired search-box widget; reStructuredText/Jinja2 for the Sphinx template
override.

**Primary Dependencies**: Sphinx (already pinned via `documentation/requirements.txt`) and
its built-in `searchindex.js` + `_static/searchtools.js` full-text search machinery
(reused, not replaced — Decision 1); `sphinx_cobra_theme` (external, read-only — only its
rendered template surface is overridden, never its source); `html5lib` (already a dependency
of `documentation/source/Contributions/UpdateSideBar.py`'s HTML parsing pattern, reused for
the new tutorial-HTML text-extraction step).

**Storage**: N/A — no database. All "storage" is static JSON/JS files shipped as part of the
published site (`searchindex.js`, generated by Sphinx; a new
`_static/json/tutorialsSearchIndex.json`, generated by this feature), regenerated in full on
every publish.

**Testing**: No `src/` MATLAB function is touched, so Principle III's MATLAB test-file
convention does not apply (see spec.md Traceability, "no-source" rows). The narrowest
practical automated check is a new Python script-level check (run as part of the new
pipeline step, and standalone/locally per `quickstart.md`) that validates the generated
tutorial supplement index is well-formed JSON and contains an entry for at least one known
tutorial page — this is the "documented reproducibility check" Principle III accepts as the
substitute when no MATLAB test file applies, and it doubles as the FR-009 fail-loudly guard.
Browser-level acceptance (does the box actually return the right results) is validated per
`quickstart.md`'s manual steps, matching this repository's existing practice for its other
documentation/CI features (e.g. 007, 012, 018 also use manual/CI verification rows, not
MATLAB test files, for non-`src` changes).

**Target Platform**: Static site served from GitHub Pages (`gh-pages` branch); build runs
headless in GitHub Actions (`ubuntu-latest`), matching the existing
`build-and-publish-docs.yml` job. The search widget itself runs client-side in the visitor's
browser — no server-side component, consistent with the site's fully static hosting model.

**Project Type**: Documentation/CI-tooling feature — no `src/` (MATLAB) change; changes are
confined to `documentation/` (Sphinx sources, a new Python indexing script, a new local
template override) and `.github/workflows/build-and-publish-docs.yml` (one new step).

**Performance Goals**: Search results must feel instant while typing (SC-003: appear within
1 second on a standard broadband connection), matching the current widget's already-instant
feel; the added pipeline step must not materially lengthen the documentation build (no
numeric target given by the spec beyond "the pipeline continues to complete successfully,"
SC-006).

**Constraints**: `sphinx_cobra_theme` MUST NOT be edited — it is fetched from a separate
GitHub repository at CI build time and is not part of this repository's tree at all (Decision
3, `research.md`); only Sphinx's local `_templates/` override mechanism may be used to change
its rendered output. The search-content generation step MUST fail the build visibly on
failure rather than publish a broken/missing search bar (FR-009). No content that is not part
of the actual published `build/html/` output may be surfaced by search (FR-007).

**Scale/Scope**: One new Python script (tutorial HTML → supplemental JSON index) of the same
order of size/complexity as the existing `UpdateSideBar.py`; one new CI step in
`build-and-publish-docs.yml`, inserted after the existing "Bring existing tutorials into
staging" step; one new/overridden Sphinx template
(`documentation/source/_templates/searchbox.html` or whatever name is confirmed against the
installed theme at implementation time) plus its inline/linked JS rewired to query the merged
index instead of `functions.json` alone. No change to `src/`, `test/`, or any MATLAB file.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Scientific code quality**: N/A — no stoichiometric matrix, model field, solver, or
  formulation code is touched. This feature changes only documentation-site build tooling
  and a client-side search widget.
- **Testing and reproducibility**: No `src/` MATLAB function under test, so Principle III's
  `test<FunctionName>.m` convention does not apply (no-source convention, per spec.md
  Traceability). The narrowest practical checks: (1) a script-level well-formedness/coverage
  check on the generated tutorial supplement index, run in CI as part of the new step so a
  broken generator fails the build (satisfies FR-009); (2) the manual/CI verification
  scenarios in `quickstart.md`, matching the acceptance-scenario/CI-verification rows already
  declared in spec.md's Traceability table.
- **User experience and diagnostics**: The visitor-facing change is the search box itself —
  it must keep the current instant, no-navigation interaction (FR-005) and must visually
  distinguish result kinds (function vs. doc vs. tutorial) so a mixed result set stays
  legible (Edge Cases in spec.md). No new console/diagnostic output is introduced; the CI
  step's only new "diagnostic" is failing loudly (non-zero exit) when it cannot produce a
  valid index, per FR-009.
- **Performance and numerical integrity**: N/A to numerical/solver integrity (no solver
  invoked). The one performance goal is SC-003 (results feel instant, <1s) which is
  subordinate to correctness of results, not traded against it — Decision 1 in `research.md`
  reuses Sphinx's already-shipped search index specifically to avoid introducing a slower or
  less-correct bespoke matcher. No diagnostic/verification step is made skippable for speed.
- **External-solver configuration audit**: N/A — no external optimization solver or library
  of that kind is invoked by this feature.
- **Spec-driven scope control**:
  - Edit: `.github/workflows/build-and-publish-docs.yml` (one new step, inserted after the
    existing tutorials-staging step).
  - New file: a Python script under `documentation/source/sphinxext/` (naming/exact location
    fixed in `tasks.md`) that emits the tutorial supplemental search index.
  - New/edited file: `documentation/source/_templates/` (a new or overridden template
    covering the search box), matching the existing local-override pattern already used by
    `index.html`/`indexsidebar.html` in that directory.
  - Read-only / MUST NOT touch: `external/`-style out-of-repo dependency
    `opencobra/sphinx_cobra_theme` (not part of this repo's tree — nothing to edit there);
    any `src/`, `test/`, or other MATLAB file; `documentation/generateJSONList.py` and
    `documentation/createModulesPage.sh` are pre-existing, currently-uncalled scripts unified
    with a different purpose (per-section function-list dropdowns) — left untouched, not
    repurposed, to avoid scope creep into unrelated, already-working page furniture.
- **MATLAB coding standards**: N/A — no MATLAB code is added or changed by this feature.
- **Parameter-setting fidelity**: N/A — this feature ports no code into another language and
  renders no literate document from MATLAB source; it is net-new documentation-site tooling.
- **Artifact placement**: New Python script → `documentation/source/sphinxext/` (existing
  home for build-time Python tooling: `GenerateCitationsRST.py`, `copy_files.py`,
  `linkcode.py` already live there — Principle IX: "documentation source →
  `documentation/`"). New/overridden Sphinx template →
  `documentation/source/_templates/` (existing, already-used location for local theme
  overrides). Generated index files (`searchindex.js`, the new
  `tutorialsSearchIndex.json`) land under `build/html/_static/` during the build and are
  staged into `ghpages/stable/` by the existing rsync steps — generated output, correctly
  never committed to `documentation/source/` (Principle IX: "generated HTML is not committed
  to source"). No file changes location relative to its established role.

No Constitution Check violations to justify.

| Item | Note |
|------|------|
| Overriding an external theme's template without access to that theme's own repository | Not a violation — Sphinx's `templates_path` override mechanism is the standard, sanctioned way to change themed output from the site that consumes a theme, and this repo already uses it for two other templates (`index.html`, `indexsidebar.html`).
