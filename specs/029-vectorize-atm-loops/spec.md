# Feature Specification: Vectorize the stage02 reorientation loop and createBIGraph's edge-expansion loop in identifyConservedReactingMoieties.m

**Feature Branch**: `029-vectorize-atm-loops`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "Vectorize two MATLAB performance hotspots in identifyConservedReactingMoieties.m's conserved-moiety-only path, both discovered via manual stage-level tic/toc instrumentation (MATLAB Profiler overhead measured at ~340x makes the built-in profiler impractical for this function) and independently validated in the reconXmoieties repo across 8 real subsystem fixtures (phe, urea, andest, nglycan, chol, tyr, bileacid, pufa) ranging from 9x3 to 924x682 (metabolites x reactions): (1) the stage02 atom-transition-edge reorientation loop (inline code, lines ~303-345, no separate function name), which rebuilds each edge's Trans string and re-indexes HeadAtomIndex/TailAtomIndex/HeadAtom/TailAtom one row at a time via scalar table dot-indexing -- replaced by reorientATMEdgesVectorized.m using cellfun for string manipulation and bulk logical indexing for the reverse-edge swap, validated isequal on all 8 fixtures with 17x-1150x speedup; (2) the stage05 createBIGraph.m call, whose internal loop grows the edge table via repeated [array; x] concatenation (O(n^2)) once per repeated bond edge -- replaced by createBIGraphVectorized.m using repelem to expand edges by weight in one vectorized pass, validated isequal Nodes/Edges tables on 7 of 8 fixtures (bileacid excluded: its buildAtomAndBondTransitionMultigraph call fails before createBIGraph is ever reached, a pre-existing SCP2x.rxn atom-mapping issue unrelated to this fix) with 30x-15557x speedup. Both fixes are pure algorithmic rewrites with no signature or behavior change, targeting identifyConservedReactingMoieties.m and createBIGraph.m only for now (conserved-moiety-only path); no other callers of createBIGraph.m are in scope for this feature."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - The atom-transition-edge reorientation step stops rebuilding strings and re-indexing one row at a time (Priority: P1)

A researcher runs identifyConservedReactingMoieties (either the conserved-moiety-only path or the full reacting-moiety path, since both run this code unconditionally before branching) and the stage02 reorientation step -- which corrects `ATM.Edges`' `Trans`, `HeadAtomIndex`, `TailAtomIndex`, `HeadAtom`, and `TailAtom` columns wherever the directed-to-undirected multigraph conversion flipped an edge's orientation -- completes without a scalar `for i=1:nTransInstances` loop that rebuilds each `Trans` string with `strtok` and reassigns four other fields via per-row table dot-indexing.

**Why this priority**: manual stage-level instrumentation (the built-in MATLAB Profiler's ~340x overhead on this function makes it impractical to run directly) measured this step at 20.8% of total pipeline time on the Tyrosine subsystem benchmark (99.9% of which is this loop specifically, isolated by sub-timing). It is also the more thoroughly validated of the two fixes: the vectorized replacement (`reorientATMEdgesVectorized.m`, prototyped in reconXmoieties) has been checked for `isequal` output against the original loop on all 8 available subsystem fixtures with no exclusions.

**Independent Test**: Run test/verifiedTests/analysis/testReactingMoieties/testConservedReactingMoieties.m and confirm it still passes with every existing assertion unchanged. Separately, run identifyConservedReactingMoieties end to end on each of the 8 fixtures before and after the change, capturing `ATM.Edges` after stage02 via the reproducibility check's temporary capture hook, and confirm it is field-for-field identical in the same row order. Edge cases the fixtures may not contain (orientation-`0` rows, `Trans` without `#`, empty or single-direction tables) are covered by the harness's synthetic stage02 section.

**Acceptance Scenarios**:

1. **Given** an `ATM.Edges` table where `orientationATM2dATM(i) == 1` (forward orientation) for some row i, **When** the reorientation step runs before and after this change, **Then** `ATM.Edges.Trans{i}` is identical (the reaction-prefix substring up to and including the first `#` is stripped identically).
2. **Given** an `ATM.Edges` table where `orientationATM2dATM(i) == -1` (reversed orientation) for some row i, **When** the reorientation step runs before and after this change, **Then** `ATM.Edges.HeadAtomIndex(i)`, `ATM.Edges.TailAtomIndex(i)`, `ATM.Edges.HeadAtom{i}`, `ATM.Edges.TailAtom{i}`, and `ATM.Edges.Trans{i}` are all identical, with head/tail correctly swapped.
3. **Given** the Tyrosine metabolism subsystem benchmark (or any of the 8 reconXmoieties fixtures), **When** the full pipeline runs after this change, **Then** wall-clock time for this step is measurably lower than the pre-change baseline, and this reduction is reported, not just asserted pass/fail.
4. **Given** `nTransInstances == 0` (a degenerate model with no atom transitions), **When** the reorientation step runs, **Then** it completes without indexing errors and leaves `ATM.Edges` unchanged, matching the current loop's (vacuous) behavior.
5. **Given** the existing `sanityChecks` block immediately following the reorientation step (which re-derives and cross-checks `HeadAtomIndex`/`TailAtomIndex` against `dATM`), **When** `sanityChecks` is enabled, **Then** it continues to pass without modification.

### User Story 2 - createBIGraph stops growing its edge table one bond instance at a time (Priority: P2)

A researcher runs identifyConservedReactingMoieties and its call to `createBIGraph(BG)` (stage05, building the bond-instance multigraph `BIG` used for connected-component analysis) expands each repeated-bond edge into its constituent instances in a single vectorized pass instead of an O(n^2) loop that grows `srcNodes`, `tgtNodes`, and each edge-property array via repeated `[array; x]` concatenation.

**Why this priority**: this step measured at 17.3% of total pipeline time on the Tyrosine benchmark (99.4% of which is the `createBIGraph` call itself), with the largest raw speedups observed of either fix (up to 15,557x on the largest fixture, `pufa`, reflecting the O(n^2) loop's especially poor scaling). It is prioritized second because its prior validation had one gap: the reconXmoieties prototype (`createBIGraphVectorized.m`) was checked for `isequal` `Nodes`/`Edges` output on 7 of 8 fixtures, because `bileacid` then failed in `buildAtomAndBondTransitionMultigraph` on the `SCP2x.rxn` atom-mapping defect. That file has since been quarantined from the corpus (Clarifications), so this feature's own in-repo validation covers all 8.

**Independent Test**: Run testConservedReactingMoieties.m and confirm it still passes unmodified. Separately, call `createBIGraph` directly on the `BG` built for each of the 8 fixtures before and after this change and confirm the returned `Nodes` and `Edges` tables (including the `Weight` and `EdgeIndex` columns) are `isequal`.

**Acceptance Scenarios**:

1. **Given** a `BG` whose edges include at least one bond with `Weight > 1` (a multi-instance bond, e.g. a double bond), **When** `createBIGraph` runs before and after this change, **Then** the returned `BIG.Edges` contains the same number of expanded rows in the same order, with `Weight` set to 1 for every expanded row (matching the current implementation's behavior) and every other property column (including non-numeric/cell columns) carried over unchanged from its source edge.
2. **Given** a `BG` containing an energy node (`Element == 'E'`), **When** `createBIGraph` runs, **Then** that node and its incident edges are excluded from `BIG` identically to the current `rmnode`-based implementation.
3. **Given** the Tyrosine metabolism subsystem benchmark (or any of the 8 reconXmoieties fixtures), **When** `createBIGraph` runs after this change, **Then** wall-clock time is measurably lower than the pre-change baseline, and this reduction is reported.
4. **Given** the existing `if ~isequal(BIG.Nodes, dATM.Nodes)` check immediately following the `createBIGraph` call in identifyConservedReactingMoieties.m, **When** this change is applied, **Then** that check continues to pass under the same conditions as before (it must not start failing, and must not be silenced or removed to force a pass).
5. **Given** the `bileacid` fixture, which now reaches `createBIGraph` because `SCP2x.rxn` has been quarantined from the corpus, **When** this feature is implemented, **Then** `bileacid` is validated through the normal pipeline like every other fixture, and the `SCP2x.rxn` atom-mapping defect itself is left unfixed by this feature -- it is tracked separately.

### Edge Cases

- What happens when `BG` (post energy-node removal) has zero edges? `createBIGraph` must return a `BIG` with the same nodes and an empty `Edges` table. **Correction (found during implementation by T013a):** the pre-change implementation does *not* do this — it crashes (`MATLAB:table:UnrecognizedVarNameDeleting`, `createBIGraph.m` line 81), because assigning `[]` to a table column deletes it. This feature deliberately fixes that (Clarifications): it is the one intentional behaviour change in the feature.
- What happens when every edge in `BG` has `Weight == 1` (no repeated bonds at all)? The vectorized expansion must produce exactly one output row per input edge, identical to today, so the fix must not regress the already-fast common case.
- What happens when an edge property column in `BG.Edges` is a cell array of strings rather than numeric? The vectorized replacement's row-index-based expansion must handle both column types identically to the current per-element copy loop.
- What happens when `orientationATM2dATM` is all `1` (no reversed edges) or all `-1` (every edge reversed) for a given fixture? Both branches of the vectorized reorientation must be exercised and correct even when one branch's input set is empty.
- The existing small CI fixture(s) used by testConservedReactingMoieties.m have very few atom transitions and bonds -- both fixes must not regress correctness at that trivial scale even though their benefit is invisible there. (Overhead at this scale is not separately measured: vectorized replacements of per-row loops are not expected to be slower, and any regression would show up as a slower CI run rather than a correctness failure.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: identifyConservedReactingMoieties.m's stage02 reorientation loop (currently lines 321-335, the `for i=1:nTransInstances` block) MUST be replaced by a vectorized implementation that produces an `ATM.Edges` table identical (`isequal`) to the current loop's output for the `Trans`, `HeadAtomIndex`, `TailAtomIndex`, `HeadAtom`, and `TailAtom` columns, in the same row order, for both the forward (`orientationATM2dATM == 1`) and reversed (`orientationATM2dATM == -1`) cases.
- **FR-002**: The FR-001 replacement MUST NOT alter `nTransInstances`, `orientationATM2dATM` itself, or any `ATM.Edges` column not listed in FR-001.
- **FR-003**: createBIGraph.m's edge-expansion loop (currently lines ~38-61, the nested `for edgeIdx = 1:numEdges` / `for bInstance = 1:bondMult` loop using repeated `[array; x]` concatenation) MUST be replaced by a vectorized implementation (e.g. `repelem`-based row-index expansion) that produces `BIG.Nodes` and `BIG.Edges` tables identical (`isequal`) to the current implementation's output, for every property column present in `BG.Edges` at the time of the call, including the `Weight` column (always set to 1 per expanded instance, matching current behavior) and the `EdgeIndex` column assigned after edge construction. **Sole exception**: when no edges remain after energy-node removal, the pre-change implementation errors rather than returning output, so there is nothing to be identical to; the rewrite instead returns `BIG` with the non-energy nodes and a zero-row `Edges` table (Clarifications, zero-edge entry).
- **FR-004**: createBIGraph.m's public signature (`BIG = createBIGraph(BG)`) MUST NOT change (Constitution Principle II). `createBIGraph.m` has exactly one caller in the entire src/ tree (identifyConservedReactingMoieties.m, line 566), so this feature MAY change its internal implementation freely as long as this input/output contract is preserved.
- **FR-005**: identifyConservedReactingMoieties.m's own public signature and documented outputs (`arm`, `moietyFormulae`, `reacting`) MUST NOT change.
- **FR-006**: The existing `sanityChecks` block immediately following the stage02 loop and the existing `if ~isequal(BIG.Nodes, dATM.Nodes)` check immediately following the `createBIGraph` call MUST continue to pass, unmodified, after both fixes are applied.
- **FR-007**: This feature MUST NOT attempt to fix or otherwise touch the pre-existing `SCP2x.rxn` atom-mapping defect -- that issue is out of scope and tracked separately. The file has been quarantined from the corpus out-of-band by the user (moved to `atomMapped_std/flagged_for_review/`), which is what allows `bileacid` to complete; this feature neither performs nor depends on reversing that quarantine.
- **FR-008**: This feature MUST NOT modify `createBIGraph.m`'s production callers beyond its existing single call site in identifyConservedReactingMoieties.m, and MUST NOT introduce any new production caller under `src/`. Test and validation callers are expected and permitted: the new CI test `testCreateBIGraph.m` and the non-CI reproducibility harness both call `createBIGraph` directly by design.
- **FR-009**: test/verifiedTests/analysis/testReactingMoieties/testConservedReactingMoieties.m MUST continue to pass after this change with every existing assertion intact -- none loosened, removed, or replaced.
- **FR-010**: The feature MUST include a documented, non-CI reproducibility check (Constitution Principle III's substitute for a full automated test, given the reconXmoieties fixtures' external model dependencies and multi-minute-to-multi-hour runtime at larger sizes), reusing or extending the `tyrosineReproducibilityCheck.m` mechanism introduced by feature 021 and extended by feature 022, that: (a) captures `ATM.Edges` after stage02 (via a temporary capture hook reverted before commit, since `ATM` is internal and never returned) and `BIG.Nodes`/`BIG.Edges` (by calling `createBIGraph` directly on the build output `BG`, which is not modified before the in-function call) as a golden snapshot BEFORE this change, across the fixture set defined by FR-011, (b) re-runs the same fixtures AFTER the change and asserts structural equality (`isequal`) against that snapshot, and (c) reports before/after wall-clock timing for both the stage02 loop and the `createBIGraph` call. Every snapshot and results entry MUST record corpus provenance (corpus path, top-level `.rxn` count, and the contents of `flagged_for_review/`), and compare mode MUST report a provenance difference as a corpus change rather than as a code regression (Clarifications).
- **FR-011**: The FR-010 reproducibility check MUST cover all 8 reconXmoieties fixtures (`phe`, `urea`, `andest`, `nglycan`, `chol`, `tyr`, `bileacid`, `pufa`) in both capture and compare mode, with no exceptions (Clarifications, Session 2026-09-18), all through the normal pipeline for both user stories. Because `pufa` alone costs hours per run, the check MUST be per-fixture resumable — each fixture's snapshot and results stored independently, so an interrupted or long-running fixture does not invalidate or require re-running the others.

### Key Entities

- **`ATM.Edges`**: existing table inside identifyConservedReactingMoieties.m's stage02 section (the undirected atom transition multigraph's edge table). The columns touched by User Story 1's fix are `Trans`, `HeadAtomIndex`, `TailAtomIndex`, `HeadAtom`, and `TailAtom`; unchanged by this feature in shape or meaning.
- **`BIG` (bond instance graph)**: existing `digraph` output of `createBIGraph.m`, with `Nodes` and `Edges` tables (the latter including `Weight` and `EdgeIndex`); unchanged by this feature in shape or meaning.
- **reconXmoieties validation fixtures**: the 8 named subsystem models (`phe`, `urea`, `andest`, `nglycan`, `chol`, `tyr`, `bileacid`, `pufa`; 9x3 to 924x682 metabolites x reactions) already used, outside cobratoolbox, to empirically validate both fixes via `isequal` checks and wall-clock timing.

## Assumptions

- The reconXmoieties fixture set and its already-collected validation artifacts (`createBIGraphVectorized_validation.xlsx`, `reorientATMEdgesVectorized_validation.xlsx`, and their source CSVs) remain available as the empirical starting point for this feature's reproducibility check; the plan phase re-runs equivalent checks directly against the src/ functions (not the reconXmoieties standalone copies) before this feature is considered complete, since the reconXmoieties prototypes are reference implementations, not the shipped code.
- `reorientATMEdgesVectorized.m` and `createBIGraphVectorized.m`, as prototyped in reconXmoieties, demonstrate a validated *approach* for this feature; the plan phase may adapt their exact code to match cobratoolbox's MATLAB coding standards and in-repo conventions (Constitution Principle VII) rather than pasting them in verbatim.
- Both hotspots (stage02 at lines 321-335, the `createBIGraph` call at line 566) execute unconditionally before the `conservedMoietiesOnly` branch point (line 1481), so this feature benefits both the conserved-moiety-only path (the one directly profiled and validated so far) and the full reacting-moiety path, even though only the former has been directly measured.
- The corpus is the post-quarantine state: `SCP2x.rxn` sits in `atomMapped_std/flagged_for_review/`, and `SCP2x` appears in no fixture except `bileacid`. All golden baselines are captured against this state; earlier `bileacid` captures, including the reconXmoieties prototype runs, are not comparable (see FR-007, FR-010).
- Only identifyConservedReactingMoieties.m and createBIGraph.m are in scope. `createBIGraph.m` has no other callers in src/ today, so no other call site is affected; any similar per-row table-indexing or array-growth pattern elsewhere in the codebase is out of scope and would need its own feature.
- This feature is independent of, and does not depend on, the work on branch 028 (reacting-moiety-cardinality-swap timing instrumentation near the STEP 4 set-cover section, committed 2026-09-18 as b374cb0ab and not merged into this branch) -- the two touch different, non-overlapping sections of identifyConservedReactingMoieties.m.
