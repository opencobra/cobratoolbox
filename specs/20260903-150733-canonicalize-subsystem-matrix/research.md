# Phase 0 Research: Subsystem Matrix Canonicalization

All findings below were confirmed by direct headless execution (`matlab -batch`, `initCobraToolbox(false,'agent')`, `test/models/mat/ecoli_core_model.mat` plus a synthetic multi-subsystem fixture derived from it), not inferred from reading source alone — per Constitution Principle V ("relevant file(s) MUST be read and mapped before editing") and III ("a numerical or solver change is not complete until the relevant execution path has been inspected"). Probe scripts are not part of the feature; they lived in the session scratchpad and are not committed.

## R1. `ecoli_core_model.mat`'s current `subSystems` shape

**Decision**: `test/models/mat/ecoli_core_model.mat` (used by `testVerifyModel.m` and as the base fixture in this plan) stores `subSystems` in the **flat-char-per-reaction** legacy shape — `class(model.subSystems)` is `cell`, `95x1`, and every `model.subSystems{i}` is itself `char` (e.g. `model.subSystems{20} == 'Exchange'`). `convertOldStyleModel.m`'s loader message confirms this: `"Each model.subSystems{x} is a character array, and this format is retained."`

**Rationale**: This is the baseline fixture new fixtures/tests in this feature must build on (via `modelSub = model; modelSub.subSystems{i} = {...}` mutation), matching the pattern `testVerifyModel.m` already uses.

**Alternatives considered**: Using `test/models/mat/Recon2.v04.mat` (already loaded by `testSammi.m`'s subsystem-grouping case) as the multi-subsystem-native fixture instead of synthesizing one — viable for the `sammi.m` test (see R4), not needed elsewhere since `ecoli_core_model` plus a targeted mutation is smaller and faster for unit-level tests.

## R2. `testVerifyModel.m`'s existing `subSystems` assertion is currently dead code

**Decision**: Executing `verifyModel`'s exact existing test scenario end to end shows the assertion never exercises real validation logic today, for two independent reasons:

1. `modelSub.subSystems(20) = {'blubb'}` keeps the value `ischar` (`'blubb'` is still a plain string). The *raw*, pre-workaround output of `checkPresentFields` (called directly, bypassing `verifyModel`'s later suppression) has **no** `subSystems` entry in `propertiesNotMatched` at all — under today's `iscell(x) && all(cellfun(@(y) ischar(y), x))` regex, `'blubb'` was never invalid to begin with. The test's premise ("test whether the correct 'invalid' subSystem is found") does not currently hold.
2. Consequently `verifyModel(modelSub,'silentCheck',true)` returns a result where `isfield(res,'Errors')` is **false** — the model has zero field-check problems overall, so `results = struct()` (line 129-131 of `verifyModel.m`) resets before the `subSystems`-suppression workaround even has anything to strip. The test's guard `if isfield(res,'Errors') ... assert(isequal(res.Errors.propertiesNotMatched.subSystems, ...))` is therefore never entered — the assertion inside it has not actually run in this test in its current form.

**Rationale**: This resolves the spec's open Edge Case/Assumption without guessing. It means: (a) fixing `verifyModel`'s suppression (FR-006) does not risk breaking a currently-meaningful assertion — there isn't one to break; (b) `testVerifyModel.m`'s existing scenario must be given a genuinely invalid value (not a still-`ischar` string) to actually exercise the fixed validator, so this test needs a content change, not just tolerance for it (US4 explicitly owns `testVerifyModel.m`; it is not one of the four "must stay unchanged" tests pinned by FR-008/SC-005).

**Alternatives considered**: Leaving `modelSub.subSystems(20) = {'blubb'}` as-is and treating "no error reported" as the expected new behavior — rejected because it would leave the malformed-content path (spec Acceptance Scenario US4.3) completely unverified by this test, defeating the purpose of US4.

## R3. `model2JSON`'s multi-subsystem data loss, confirmed reproducible

**Decision**: Built a fixture where `model.subSystems{1} = {'Glycolysis','Pentose Phosphate'}` and ran `model2JSON` on it. The emitted JSON for that reaction contains exactly `"subsystem":"Glycolysis"` — `Pentose Phosphate` does not appear anywhere in the file. This confirms `model2JSON.m:172-177`'s `try`/`catch` fallback (`a=model.subSystems{i}; ...a{1}...`) silently keeps only the first name, exactly as read from source.

**Rationale**: Directly grounds FR-001/SC-001 and the `testModel2JSON.m` fixture to be authored at `/speckit-tasks`/implementation: a reaction with >1 subsystem, asserting the JSON contains every name (not merely that parsing succeeds).

## R4. `sammi.m`'s subsystem grouping does not "misbehave" on multi-subsystem models — it throws

**Decision**: Reproducing `sammi.m:160`'s exact expression, `model.rxns(ismember(model.subSystems, ss{i}))`, against a `subSystems` field where every entry is uniformly a cell array (the realistic nested/multi-subsystem shape — matching what `convertOldStyleModel.m` produces when *any* reaction has more than one subsystem, not a mix of char and cell) **errors**: `Input A of class cell and input B of class char must be cell arrays of character vectors, unless one is a character vector.` This is a harder failure than the spec's User Story 2 description ("silently omitted from some or all of the subgraphs") — `sammi(model,'subSystems')` cannot complete at all for such a model today, it does not just produce an incomplete result.

**Rationale**: This refines (does not contradict) spec FR-004 — the required behavior ("include a reaction in every subgraph it belongs to") is unchanged, and the acceptance scenarios still hold; the fix must replace the direct `ismember` comparison with a lookup that tolerates a cell-of-cells entry (the same normalization `isReactionInSubSystem`/`findRxnsFromSubSystem` already apply via `rxn2subSystem`). Recorded here so the implementer isn't surprised when the "before" state of the regression test is a thrown error rather than a wrong-but-silent result.

**Alternatives considered**: None — this is a factual finding, not a design choice.

**Correction (found during `/speckit-implement`, 2026-09-07)**: Direct execution against the exact fixture this plan specifies (`quickstart.md` Step 3's `modelUniform`, and the mixed-shape variant) shows the error above is **not reproducible as described**. `unique(model.subSystems)` — `sammi.m:156`, which runs *before* line 160's `ismember` — throws first, for both the uniformly-nested and mixed-shape fixtures, with MATLAB's own message `Cell array input must be a cell array of character vectors.` (confirmed via stack trace: `unique` -> `sammi` line 156). The `ismember`-style message quoted above was never observed in this session; the fix therefore replaces the `ss = unique(model.(parser))` computation itself for the `'subSystems'` case (not only line 160's `ismember`), which the implementation (`sammi.m`'s new `strcmp(parser,'subSystems')` branch) already does by building `subSystemNames`/`rxn2subSystem` via `buildRxn2subSystem` instead of `unique`. This does not change FR-004's required behavior, only which exact line/message the "before" state exhibits.

**Second finding (found during `/speckit-implement`, 2026-09-07)**: Fixing the grouping alone (`dat` construction) is **not sufficient** for `sammi(model,'subSystems',...)` to complete without error on a nested-cell model. `structParse`/`makeSAMMIJson` (called by every branch of `sammi.m`, not only the `'subSystems'` one) treat every model field whose size matches `.rxns` — `subSystems` included — as a generic per-reaction JSON annotation, and its serialization loop (`makeSAMMIJson.m:71-87`) assumes a uniform cell-of-char shape; a nested-cell `subSystems` entry throws there (`strjoin` on a non-uniform cell, `Error in makeSAMMIJson (line 87)`), *after* the grouping fix succeeds. This is a pre-existing defect in `makeSAMMIJson.m`'s generic field handler, latent for **any** `sammi()` call (any `parser` value) on a model whose `subSystems` uses either cell legacy shape — it was previously unreachable only because no test ever exercised a cell-shaped `subSystems` model through `sammi()` at all. Fixing `makeSAMMIJson.m` itself is out of scope (not a file this feature's plan lists as touched, and the defect is general-purpose, not `subSystems`-specific). The chosen fix stays inside `sammi.m`: immediately after argument defaulting, a reaction whose `subSystems` entry is a cell (either legacy cell shape) is flattened to a `;`-joined string on a **local copy** of `model.subSystems` only (matching `model2JSON.m`'s new convention — FR-001), before any `structParse`/`makeSAMMIJson` call; the `'subSystems'`-grouping branch captures the raw, unflattened shape first (`subSystemsRaw`) so multi-subsystem membership is still computed correctly. The caller's `model.subSystems` is never touched (FR-011) since MATLAB is pass-by-value and no output argument returns `model`.

## R5. `getModelSubSystems`/`buildRxn2subSystem` already handle nested-cell input correctly today

**Decision**: On the same multi-subsystem fixture, `getModelSubSystems` returns the correct 12-name de-duplicated list (order-stable, alphabetical via `unique`), and `buildRxn2subSystem` correctly detects `nestedCells=true`, builds a `95x12` matrix, and maps reaction 1 to exactly the two correct columns (`Glycolysis`, `Pentose Phosphate`).

**Rationale**: Confirms User Story 3's premise directly: there is no output-correctness defect in `getModelSubSystems` today, so FR-003's requirement is purely an internal-consistency refactor (route its computation through the same matrix construction `buildRxn2subSystem` performs) with a **pre/post output-equality** test, not a behavior-fixing test — lowering implementation risk for that story.

## R6. `COBRA_structure_fields.tab` schema (for registering `rxn2subSystem`/`subSystemNames`, FR-005)

**Decision**: The file is a 15-column TSV parsed by `getDefinedFieldProperties()` via `descFileRead`, header: `Model Field, Xdim, Ydim, Evaluator, databaseid, qualifier, qualifierType, referenced Field, Default Value, DBPatterns, Property Description, Field Description, BasicFields, FieldBasisType, FBAFields`. `checkPresentFields.m` evaluates column 4 (`Evaluator`) with `x` bound to the field's value (and `model` itself in scope, since `checkPresentFields` receives `model` as an argument), and separately checks `Xdim`/`Ydim`: a numeric value is an exact dimension; a string names another field whose `numel` the dimension must equal (used today by `subSystems`'s own row `Xdim = 'rxns'`).

**Rationale**: For the two new rows: `rxn2subSystem`'s `Xdim` should reference `rxns` (row count = `numel(model.rxns)`) and `Ydim` should reference `subSystemNames` (column count = `numel(model.subSystemNames)`), giving `checkPresentFields` a real cross-field consistency check "for free"; `subSystemNames`'s own row needs no dimension check (variable-length, like other name lists), only an `Evaluator` of `iscell(x) && all(cellfun(@(y) ischar(y), x))` — the same flat-cell-of-strings check already used for other name-list fields. Both rows' `BasicFields`/`FBAFields` columns follow existing derived-field rows (`'false(1)'` — optional, not required, not FBA-critical), matching the Assumptions section of spec.md.

**Alternatives considered**: Making the two fields required (`BasicFields = 'true(1)'`) — rejected; spec Assumptions explicitly require them to stay optional/derived so models without a matrix built yet remain valid.

## R8. FR-003 as literally written is circular; `getModelSubSystems.m` has a pre-existing unreachable branch (found during `/speckit-implement`, 2026-09-07)

**Decision**: `buildRxn2subSystem.m:73` already reads `subSystemNames = getModelSubSystems(model);` — `buildRxn2subSystem` delegates name-enumeration *to* `getModelSubSystems`, not the reverse. FR-003's literal instruction ("`getModelSubSystems` MUST use the same rxn-by-subsystem matrix construction that `buildRxn2subSystem` already performs... as its internal mechanism") would require `getModelSubSystems` to call `buildRxn2subSystem`, which calls `getModelSubSystems` — infinite recursion. `buildRxn2subSystem.m` is out of scope (FR-008, plan.md marks it READ ONLY), so inverting the dependency there is not an option.

Separately, `getModelSubSystems.m`'s existing three-way branch (`if all(charBool) ... elseif all(cellBool) ... else ... end`, guarded by `if ~nestedCells`) has a latent, pre-existing defect: `nestedCells` is computed by the identical per-element `iscell(model.subSystems{i})` test as `cellBool`, so `nestedCells == any(cellBool)`. Inside the `~nestedCells` guard, `cellBool` is therefore already all-false, meaning `all(charBool)` is always true there — the `elseif all(cellBool)` branch (written to handle the flat-cell-of-char legacy shape) can never execute. Confirmed empirically: a uniformly-1-element-cell `subSystems` fixture sets `all(cellBool)=1` and `nestedCells=1` simultaneously, routing it into the generic nested-cells branch instead (which happens to still compute the correct result, so this was not an output-correctness defect, only dead code).

**Rationale**: FR-003 is corrected (see spec.md) from "call `buildRxn2subSystem`" to "consolidate `getModelSubSystems`'s three overlapping branches into the single flatten-then-`unique`-then-filter-empty algorithm its own nested-cells branch already uses for all three legacy shapes (removing the dead `elseif all(cellBool)` branch), verified by a pre/post output-equality test" — this delivers the spec's actual intent (remove duplicate/dead logic, one algorithm instead of three) without recursion, without touching `buildRxn2subSystem.m`, and preserves output exactly (the surviving algorithm is the one already proven correct for all three shapes by R5).

**Alternatives considered**: Changing `buildRxn2subSystem.m` to stop delegating to `getModelSubSystems` (inverting the dependency) — rejected: out of scope (FR-008 pins it unchanged) and unnecessary, since the consolidation above satisfies the spec's underlying goal without touching a frozen file.

## R7. `model2JSON` already has a test file — it is just invisible to the test harness (found during `/speckit-tasks`, corrects R3/plan.md/spec.md FR-009)

**Decision**: `test/verifiedTests/base/testIO/testModel2JSON` exists, is git-tracked (added 2024-08-15 by commit `b96d42730`, last touched by `596fc686c`), and contains a real 6-model `model2JSON` + `isValidJSON` smoke test — but the file has **no `.m` extension** and does not live in a `testModel2JSON/` subdirectory the way its siblings in the same folder do (`testIsValidJSON/`, `testKEGG/`, `testUtilities/`). `test/testAll.m:113`'s discovery call, `getFilesInDir('restrictToPattern', '^.*\.m$', ...)`, only matches `*.m` files, so this test is silently excluded from `test/testAll.m` and CI today — it has never been executed as part of the suite in this form. The earlier claim in this plan ("`model2JSON` currently has no test file") was based on a search that missed this extensionless file.

**Rationale**: This changes the FR-009/SC-001 implementation task from "create a new test file" to "rename/relocate the existing test into the constitutionally-correct path (`test/verifiedTests/base/testIO/testModel2JSON/testModel2JSON.m`, Principle III-Naming's one-file-per-function, one-directory-per-test convention already used by its siblings) and extend its existing 6-model coverage with the multi-subsystem assertions this feature requires (SC-001)." No coverage is lost — the existing loop over `{'ecoli_core_model.mat', 'Recon1.0model.mat', 'Recon2.v05.mat', 'Abiotrophia_defectiva_ATCC_49176.mat', 'Recon3DModel_301.mat', 'iJO1366.mat'}` is preserved verbatim inside the renamed file, and this is itself a pre-existing-bug fix (a dead, never-run test starts running) that is in scope as a corollary of FR-009 rather than a new defect class.

**Alternatives considered**: Leaving the file at its current name/location and creating a second, differently-named `testModel2JSON.m` alongside it — rejected outright: Constitution III-Naming explicitly forbids a second, differently-named test file for the same function, and it would leave the dead file in the tree as clutter.
